### Problèmes détaillés

---

**C1 — Build non compilable** | Gravité : Critique

- **Pourquoi** : `UserDetailsServiceImpl.java` contient un rapport Markdown complet injecté entre `@RequiredArgsConstructor` et `public class`. `ProfileAssignmentDomainService.java` ligne 134 contient le caractère `-` parasite `for (Role role : rolesToAssign) {-`.
- **Impact technique** : impossible de compiler, packager, tester, déployer.
- **Impact métier** : aucune livraison possible.
- **Solution** : extraire le Markdown vers `docs/AUDIT.md`, restaurer `UserDetailsServiceImpl` à sa seule classe Java. Corriger le `-` parasite.
- **Recommandation** : P0 immédiat, aucun autre chantier ne démarre tant que `./gradlew test` ne passe pas. Ajouter une CI qui empêche tout merge si `compileJava` échoue.

---

**C2 — Module `gestion-user` à mauvais namespace** | Gravité : Critique

- **Pourquoi** : Les fichiers physiques sont sous `src/main/java/com/school/management/gestion-user/` mais déclarent `package com.erp.school.domain.model.identity`. Java interdit les tirets dans les noms de packages. Le component-scan Spring et JPA scan ne peuvent pas résoudre ces classes.
- **Impact technique** : imports cassants, entités non détectées par Hibernate, beans Spring introuvables.
- **Impact métier** : le futur bounded context Identity & Access est non fonctionnel.
- **Solution A** : renommer tous les packages vers `com.school.management.identityaccess` et déplacer les fichiers dans le bon répertoire. Avantage : rapide. Inconvénient : nécessite de mettre à jour tous les imports.
- **Solution B** : extraire en module Gradle indépendant `identity-context` avec son propre `src`. Avantage : frontière propre dès le départ. Inconvénient : plus de travail.
- **Recommandation** : Solution A en urgence pour restaurer la compilabilité, Solution B sur la roadmap Phase 3.

---

**C3 — Architecture hybride sans gouvernance** | Gravité : Élevé

- **Pourquoi** : Le monolithe est en couches techniques (`controller/service/repository/model`). Les sous-services sont en hexagonal. `gestion-user` tente DDD. Aucune règle d'architecture n'est documentée ni vérifiée par des outils comme ArchUnit.
- **Impact** : chaque développeur suit son propre pattern, la dette technique s'accumule exponentiellement.
- **Solution** : documenter l'architecture cible et la faire appliquer via ArchUnit dans la CI.

---

**C4 — Double source de vérité pour les présences et les paiements** | Gravité : Élevé

- **Pourquoi** : `AttendanceController` dans le monolithe et `attendance-service` exposent tous deux des APIs attendance. `PaymentController` dans le monolithe et `billing-service` exposent tous deux des APIs paiement.
- **Impact** : données potentiellement divergentes, frontend incertain sur quel endpoint consommer.
- **Solution** : décider la source de vérité par domaine. Le monolithe doit déléguer ou être mis en lecture seule pour ces deux domaines.

---

**C5 — `PaymentController` est un service applicatif, pas un controller** | Gravité : Élevé

- **Pourquoi** : `PaymentController` injecte directement `PaiementRepository`, `StudentRepository`, `InscriptionStudentRepository`, `MontantRepository`. Il contient 400+ lignes de logique métier (calcul du montant restant, validation des règles de remise, parsing des payloads `Map<String,Object>`).
- **Impact** : violation totale du SRP et de la Clean Architecture. Non testable unitairement. Toute évolution nécessite de modifier le controller.
- **Solution** : créer un `PaymentService` ou use case `RecordPaymentUseCase` et déplacer toute la logique. Le controller ne doit contenir que la translation HTTP ↔ commande.

---

**C6 — `GradeService` : God Class** | Gravité : Moyen-Élevé

- **Pourquoi** : 340+ lignes de code. Responsabilités mélangées : CRUD, calcul de moyennes, calcul de rang, génération de rapport de classe, gestion du cache, notification.
- **Impact** : non testable, fragile aux modifications, couplage fort avec `NotificationService`, `GradeRepository`, `StudentRepository`, `SubjectRepository`, `SequenceRepository`, `TrimestreRepository`, `ClasseRoomRepository`.
- **Solution** : décomposition déjà partiellement commencée (`GradeCommandService`, `GradeQueryService`, `GradeCalculationService`) mais `GradeService` reste et contient encore tout.

### Ce qui manque globalement

**Value Objects absents** :
- `Money` — présent dans `billing-service` seulement, absent du monolithe où `BigDecimal` est utilisé directement sur `Paiement`
- `StudentNumber` — `String` libre non validé
- `GradeScore` — `BigDecimal` nu sur `Grade`, contraintes dans l'entité JPA mais pas dans un VO
- `SchoolYearCode` — `String` libre
- `Coefficient` — `BigDecimal` nu
- `ReceiptNumber` — `String` libre, généré par `"PAY-" + id` dans le controller
- `PhoneNumber`, `EmailAddress` — String libres

**Domain Events absents** du monolithe :
- `StudentRegistered`
- `PaymentReceived`
- `GradeRecorded`
- `EnrollmentCreated`
- `AbsenceMarked`

**Aggregates non définis** : aucun aggregate root explicite dans le monolithe. `InscriptionStudent` devrait être l'aggregate root du contexte Enrollment mais n'a pas d'invariants de domaine.

**Factories absentes** : tous les objets sont construits dans les services.

**Domain Services absents** : `GradePolicy`, `EnrollmentPolicy`, `BillingPolicy`.

### Analyse de `InscriptionStudent` — problème majeur

```java
// Problème 1 : statut en String libre au lieu d'enum

// Problème 2 : champ avec majuscule (nommage Java invalide)
private LocalDate DateInscription;

// Problème 3 : cascade PERSIST vers Student —

@ManyToOne(cascade = CascadeType.PERSIST)

// Problème 4 : pas d'invariant d'unicité — un même élève

```

### Analyse de `Grade` — problème de modèle

```java
// Redondance : sequence + trimestre + period (String)
// Trois façons différentes de représenter la même période
private Sequence sequence;     // FK vers séquence
private Trimestre trimestre;   // FK vers trimestre
private String period;         // String libre dupliqué
```

Cela indique un modèle migré partiellement, avec des données incohérentes potentielles en base.

### Analyse de `Users` — problème de sécurité + design

```java
// @Pattern sur le mot de passe est appliqué au hash BCrypt
// Tous les hashes BCrypt commencent par "$2a$12$..." 
// ce qui ne matche pas le pattern attendu pour un mot de passe en clair
@Pattern(
  regexp = "^(?=.*[a-z])(?=.*[A-Z])(?=.*\\d)(?=.*[.\\-_@$!%*?&#])...$"
)
private String password;
```

Ce pattern doit être appliqué uniquement à la validation du DTO de création/changement de mot de passe, jamais sur l'entité persistée.
