## PARTIE 2 : AUDIT DE L'ARCHITECTURE

### Vue d'ensemble

Le projet présente **quatre niveaux architecturaux simultanés** dans un même monolithe, ce qui est le premier signal d'alarme critique :

```
Niveau 1 (Legacy)     : com.school.management.model / service / repository / controller
Niveau 2 (Shared)     : com.school.management.shared.*
Niveau 3 (DDD expérimental) : com.school.management.gestion-user (dossier invalide)
Niveau 4 (Infrastructure) : com.school.service (package racine !)
```

### Analyse par critère

#### Adaptation de l'architecture
**Note : 3/10**

Le projet démarre comme un CRUD monolithique classique, puis tente d'introduire des couches DDD et hexagonale **en parallèle** sans refactorisation du code existant. Le résultat est une architecture schizophrène : des classes comme `AbstractService<D, E extends BaseEntity<ID>, ID, R, M>` coexistent avec des services de 300 lignes qui font du CRUD direct.

**Problème** : Aucune frontière architecturale n'est respectée. Le `StudentService` (legacy) et le `StudentCommandService` + `StudentQueryService` (CQRS partiel) font la même chose, créant une duplication.

**Impact** : Chaque développeur peut choisir n'importe quel style, rendant le code imprévisible.

**Gravité : Critique**

#### Respect DDD
**Note : 2/10**

Il n'y a pas de vrai DDD dans ce projet. On observe :
- Pas d'Aggregate Roots définis — `Student`, `Grade`, `Paiement` sont des entités JPA sans frontières d'agrégat
- Pas de Domain Events
- Pas de Value Objects — `Email`, `PhoneNumber`, `Money`, `StudentNumber` sont de simples `String`/`BigDecimal`
- Pas d'Ubiquitous Language cohérent : mélange français/anglais dans les noms (`lastnameTeacher`, `dateEmbauche`, `libelleSequence`, `nameClasse`)
- Les règles métier sont dans les Services (couche application), pas dans le domaine
- `UserRole` dans le fichier actif EST un bon début DDD, mais isolé et non branché

#### Respect SOLID
**Note : 4/10**

- **SRP** violé massivement : `StudentService` (legacy) gère création, mise à jour, suppression, rapports, statistiques, export — 5 responsabilités dans une classe. `GradeService` est un monstre de ~450 lignes.
- **OCP** : `IGenericService` / `AbstractService` est une tentative, mais la plupart des services ne l'utilisent pas
- **LSP** : pas applicable à ce niveau
- **ISP** : `IGenericService` expose `findAll()` sans pagination et `findAll(Pageable)` — deux méthodes redondantes
- **DIP** : Les services injectent directement les implémentations de Repository JPA au lieu d'injecter des ports abstraits

#### Respect Clean Architecture
**Note : 2/10**

- La règle de dépendance est inversée en permanence : les entités JPA (`@Entity`) **sont** les entités de domaine — le domaine dépend de JPA (infrastructure)
- Les mappers convertissent des DTOs ↔ Entités JPA, pas des DTOs ↔ objets de domaine purs
- Le domaine (`model/`) importe `jakarta.persistence.*` — violation directe

#### Respect Hexagonal Architecture
**Note : 2/10**

Le module `gestion-user` tente une architecture hexagonale (ports/adapters) mais :
- Les sources Java sont **absentes** (uniquement des `.class`)
- Le reste du projet ignore totalement ce pattern
- `UserAccount` (nouveau) et `Users` (legacy) — deux systèmes d'authentification non connectés

#### Couplages inutiles
**Note : 3/10** (3 = beaucoup de couplages)

- `PaymentService` injecte `GradeService` — couplage Finance ↔ Pédagogie sans justification
- `DirectionDashboardService` injecte 6 repositories directement — couplage fort à l'infrastructure
- `InscriptionStudentService` injecte `StudentService` — couplage fort entre deux services
- `StudentService` (legacy) et `StudentCommandService`/`StudentQueryService` coexistent

#### Problèmes d'évolutivité
**Note : 3/10**

- `DirectionDashboardService.getSummary()` charge **tous les paiements** en mémoire pour itérer : `paiementRepository.findAll()` — catastrophique à l'échelle
- `InscriptionStudentService.getStudentCountBySection()` charge toutes les classes puis toutes les inscriptions par classe — N+1 queries en boucle Java
- Pas de pagination sur `StudentService.getAllStudents()` — retourne une `List` entière
- `AnalyticsService` et `PredictiveAnalyticsService` utilisent du SQL brut via `JdbcTemplate` sans pagination

#### Risques techniques
- **Critique** : Deux systèmes d'authentification (`Users/UsersProfil` vs `UserAccount/Role`) non consolidés
- **Critique** : `Users` implémente `UserDetails` — entité de domaine couplée à Spring Security
- **Critique** : `AnalyticsService` utilise `DATE_FORMAT` MySQL — couplage à MySQL (incompatible PostgreSQL ciblé)
- **Élevé** : `Subject.coefficient` est `Integer` alors que `Grade.coefficient` est `BigDecimal` — incohérence
- **Élevé** : `AnneeScolaire.statutCode` est un `boolean` — si deux années ont `true`, l'état est corrompu
- **Élevé** : Le package `gestion-user` contient un **tiret** dans son nom — invalide en Java

## PARTIE 5 : AUDIT DE LA BASE DE DONNÉES

### Problèmes identifiés

**Gravité Critique**

1. **`AnneeScolaire.statut_code` est un `boolean`** : rien n'empêche deux années d'être actives simultanément. Manque une contrainte `UNIQUE` partielle : `WHERE statut_code = TRUE`.

2. **`Montant.count`** : un champ financier nommé `count` (terme de comptage). Ambiguïté totale. Devrait s'appeler `amount`.

3. **Pas de table `user_roles` cohérente** : `UserAccount` mappe `user_roles` avec `@ManyToMany`, mais `UserRole` (DDD) est une entité séparée mappant la même table `user_roles` avec une structure différente. **Conflit de mapping JPA certain**.

4. **`Teacher` n'utilise pas `Person`** : duplication des colonnes nom/prénom/email/téléphone/genre entre `enseignant` et `persons`.

**Gravité Élevée**

5. **Pas de soft-delete cohérent** : `Users` a `actif`, `BaseEntity` a `active`, `ClasseRoom` a `actif`, `Subject` a `actif` — noms incohérents, certaines entités n'ont pas de champ soft-delete du tout (`Grade`, `Absence`, `Paiement`).

6. **`InscriptionStudent.statut_preinscription` est VARCHAR** : devrait être un ENUM avec contrainte CHECK. Les valeurs `INSCRITE`, `EN_ATTENTE`, `BROUILLON` ne sont pas controlées en base.

7. **`Sequence` et `Trimestre` sans contrainte unique** : rien n'empêche deux séquences identiques pour le même trimestre.

8. **`Grade` a un champ `period` (String) redondant avec `sequence.libelle_sequence`** : source de désynchronisation.

9. **Pas d'index sur les colonnes de recherche fréquente** : `students.student_number`, `persons.email`, `paiements.date_paiement` (seulement les colonnes de jointure).

**Gravité Moyenne**

10. **`LogActivite.date_action` est `insertable=false, updatable=false`** sans valeur DEFAULT en base — la colonne sera NULL si la base n'a pas de `DEFAULT CURRENT_TIMESTAMP`.

11. **`Subject.coefficient` est `INTEGER`** — devrait être `DECIMAL(4,2)` pour les coefficients fractionnaires (ex: 1.5).

12. **Flyway utilise MySQL** (`flyway-mysql`) mais l'objectif déclaré est PostgreSQL. Les migrations V1-V12 ont du SQL MySQL-specific (`DATE_FORMAT`, `AUTO_INCREMENT`, `DATETIME(6)`).
